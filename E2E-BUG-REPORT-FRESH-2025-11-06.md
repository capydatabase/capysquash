## Bug #10: SECURITY DEFINER Attribute Dropped from Functions

### Severity: **CRITICAL** 🔴
### Case Study: nami ai app (Clerk auth)
### Impact: Security vulnerability - functions lose elevation privileges

### Description
The `SECURITY DEFINER` attribute is being dropped from Clerk authentication functions during squashing. This is a critical security issue because `SECURITY DEFINER` causes a function to execute with the privileges of the user who created it, not the user calling it.

### Evidence

**Original** (migrations/02_rls_policies_and_functions.sql):
```sql
CREATE OR REPLACE FUNCTION current_clerk_user_id()
RETURNS TEXT AS $$
  SELECT (auth.jwt()->>'sub')::TEXT;
$$ LANGUAGE SQL STABLE SECURITY DEFINER;
```

**Squashed** (test-run-fresh/000_baseline.sql line 201):
```sql
CREATE OR REPLACE FUNCTION current_clerk_user_id() RETURNS text LANGUAGE sql STABLE AS $$
  SELECT (auth.jwt()->>'sub')::TEXT;
$$;
```

### Affected Functions
1. `current_clerk_user_id()` - Missing `SECURITY DEFINER`
2. `current_clerk_org_id()` - Missing `SECURITY DEFINER`
3. `current_clerk_org_role()` - Missing `SECURITY DEFINER`
4. `validate_jwt_version()` - Missing `SECURITY DEFINER`
5. `set_session_user()` - Missing `SECURITY DEFINER`
6. `get_planning_analytics()` - Missing `SECURITY DEFINER`

### Root Cause
The deparser or post-processing is not preserving the `SECURITY DEFINER` attribute. Need to investigate:
1. Does `pg_query.Deparse()` include `SECURITY DEFINER`?
2. Is it being stripped during post-processing?
3. Is the AST not capturing it properly?

### Proposed Fix
**Architectural Approach**:
1. Check if `SECURITY DEFINER` is in the AST (check `CreateFunctionStmt` fields)
2. If AST has it but deparser drops it, add post-processing safety net
3. Parse functions after deparsing and re-add `SECURITY DEFINER` if missing but present in original

### Test Case
```bash
cd "case studies/nami ai app"
../../pgsquash squash migrations/*.sql --safety standard --output test-security-definer
grep -c "SECURITY DEFINER" test-security-definer/000_baseline.sql
# Should equal original count (11)
```

## Bug #11: 68 Indexes Missing from Squashed Output

### Severity: **CRITICAL** 🔴
### Case Study: myroomie
### Impact: Performance degradation - queries will be extremely slow without indexes

### Description
68 indexes present in the original migrations are completely missing from the squashed output. This would cause catastrophic performance issues in production.

### Missing Indexes (sample)
```
1. idx_communities_category_id
2. idx_communities_creator_id
3. idx_community_members_community_id
4. idx_community_members_profile_id
5. idx_community_posts_author_id
6. idx_community_posts_community_id
... (62 more)
68. idx_property_interests_user_id
```

### Root Cause
Indexes are being lost during consolidation or not being tracked properly. Possible causes:
1. Indexes with same name but different definitions being incorrectly consolidated
2. Indexes on renamed columns not being updated correctly
3. Dependency ordering causing indexes to be skipped
4. Lifecycle tracking issue where indexes are marked as dropped but shouldn't be

### Proposed Fix
**Architectural Approach**:
1. Audit index tracking in `unified_tracker.go`
2. Check consolidation rules for indexes - are they being incorrectly removed?
3. Verify index dependency resolution - are they being created in correct order?
4. Add validation that final output has >= original index count (unless explicitly dropped)

### Test Case
```bash
# Count indexes in original vs squashed
grep -c "CREATE INDEX" migrations/*.sql > /tmp/original_count.txt
grep -c "CREATE INDEX" test-run-fresh/000_baseline.sql > /tmp/squashed_count.txt
diff /tmp/original_count.txt /tmp/squashed_count.txt
```

## Bug #12: 8 Functions Incorrectly Added to Squashed Output

### Severity: **HIGH** 🟠
### Case Study: myroomie
### Impact: Schema bloat - functions that shouldn't exist are created

### Description
8 functions appear in the squashed output that don't exist in the original migrations. These are likely:
1. Generated by plugins incorrectly
2. Helper functions that shouldn't be in final output
3. Consolidation artifacts

### Extra Functions
```
1. public.prevent_null_fairrent_fields
2. public.get_fairrent_model_comparison
3. public.cleanup_expired_fairrent_scores
4. public.get_valid_room_fairrent_score
5. public.calculate_user_compatibility
6. public.calculate_enhanced_lifestyle_compatibility
7. public.extract_email_domain
8. public.get_valid_fairrent_score
```

### Root Cause
Functions are being generated during consolidation or by plugins when they shouldn't be. Need to check:
1. Are these from compatibility layers?
2. Are they helper functions generated by consolidation rules?
3. Is there a plugin injecting these?

### Proposed Fix
**Architectural Approach**:
1. Only output functions that existed in original migrations
2. Compatibility layer functions should be clearly marked and optional
3. Add flag to disable generated helper functions
